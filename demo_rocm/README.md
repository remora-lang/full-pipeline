# Running Remora on an AMD GPU

`remora2rocm` compiles a Remora program to an AMD GPU, using MLIR's own GPU
pipeline throughout. It is the GPU counterpart to `../remora2exe`, but is
completely independent. It would be nice if someone did a similar demonstration
for CUDA.

The following commands assume you are in the `demo_rocm` directory (the one
containing this README).

Note the `.#rocm` below: ROCm lives in a flake output of its own, so that the
default environment is smaller.

```shell
$ nix shell .#rocm
$ ./remora2rocm ../examples/inc2.remora
built .../demo_rocm/build/libinc2.a and .../demo_rocm/build/inc2.h (kernels for gfx1100, tile 256)
link with: clang yourprogram.c .../libinc2.a -I... -L... -lmlir_rocm_runtime -lmlir_c_runner_utils -lamdhip64 -lm
built .../demo_rocm/build/inc2 from inc2_scaffold.c
$ ./build/inc2
[2, 3, 4, ..., 1024, 1025]
```

`CHIP` (default `gfx1100`) and `TILE` (default `256`) are environment variables.

The important property is that nothing about the kernel is written by hand. Its
name, launch geometry, and argument layout are all emitted by the compiler, so
the same script works for any program rather than one specific program.

The output is a library, not a program: `libinc2.a` plus a generated `inc2.h`.
`main` belongs to whoever links it. `../examples/inc2_scaffold.c` is an
example of that, and is the only hand-written C left -- it stands in for the
application a user would bring. It is shared with `../remora2exe`, since the
generated interface is the same whatever the target.

## The C API

Generated by `../remora-cbindings.janet` from the entry signatures in the MLIR, so
nothing about the interface is written by hand either. It follows Futhark's
generated C API:

```c
struct remora_context *ctx = remora_context_new();

struct remora_i64_1d *in = remora_new_i64_1d(ctx, data, 1024);
struct remora_i64_1d *out = NULL;
if (remora_entry_inc2(ctx, &out, in) != 0) {
  fprintf(stderr, "%s\n", remora_context_get_error(ctx));
}
remora_values_i64_1d(ctx, out, results);
```

Arrays are opaque handles. `remora_new_*` copies the caller's data in, so it
can be any pointer -- `malloc`'d, static, borrowed -- and the caller never
learns that the GPU cannot read most memory. `remora_values_*` copies back out.

Not taken from Futhark: there is no configuration object, and no
`remora_context_sync`, because entry points already synchronise before they
return. The context holds only the last error today; it is threaded through
every call because it is where a device handle will go later.

## Memory

Handles are backed by pinned host memory, from the same allocator that MLIR's
own `memref.alloc` goes through: `memref.alloc` would otherwise become a plain
`malloc`, which a discrete AMD GPU cannot read: gfx1100 has no XNACK, so the kernel page-faults on it. Passing
`use-generic-functions` to `--finalize-memref-to-llvm` redirects it to
`_mlir_memref_to_llvm_alloc`, which `mlir_rocm_alloc.c` implements. That file is
program-independent.

Because both sides of the boundary are pinned host memory, copying in and out is
a `memcpy` rather than a device transfer. It also means every intermediate the
kernel touches is read over PCIe rather than from device RAM -- correct, and
slow. Moving to real device memory is a change behind the handles, not to the
API.

## Shutdown

MLIR registers the GPU module unload as a static destructor, which runs after
the GPU runtime has already shut itself down and complains about a failure
nothing can be done about. The old scaffolding left through `_Exit` to skip it;
a library cannot do that to its caller, so the driver script deletes the
`llvm.global_dtors` entry instead. The module then leaks until the process ends,
which costs nothing.

## Known limitations

**The tile size must divide the iteration count.** If it does not, tiling
produces an `affine.min` bound, `--convert-parallel-loops-to-gpu` quietly
declines to convert the loop, and we get a correct CPU binary with no kernel in
it at all.

**`TILE` above 256 fails at launch.** `--rocdl-attach-target` stamps the code
object with the ROCDL default `max_flat_workgroup_size = 256`, so a 512-thread
launch returns `hipErrorLaunchFailure`. The program then prints zeroes and exits
0, which is worse than crashing. `TILE=256` matching the default is luck, not
design.

**Programs whose data is compile-time constant fault.** Bufferization turns
`arith.constant dense<...>` into a `memref.global`, which lives in the host
binary's read-only data and is not GPU-accessible; only `memref.alloc` goes
through the pinned allocator. This is why `../examples/basic0`, `basic2`,
`basic4` and `basic5` (whose inputs are all literals) fault as soon as a tile
size small enough to actually produce a kernel is used. At the default `TILE`
they silently fall back to CPU and compute the right answer, which is a
confusing way to be wrong. A global returned *as a result* would be worse still,
since `remora_free_*` would hand read-only data to the pinned deallocator; no
entry point in `../examples` does that today, and fixing the lowering removes
the risk. `inc2` is unaffected because its input comes from the caller. Fixing
this properly means copying such globals into device-visible memory during
lowering.

**One Remora library per binary.** Entry points keep their MLIR names, so the
four `../examples/basic*` programs all define `entry_main` and cannot be linked
together. Futhark has the same constraint.

**A result may not alias an argument.** It would be freed twice. Nothing the
pipeline emits today does this, and the bindings check for it and fail rather
than let it through.
